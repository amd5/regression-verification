# 覆盖审计

## 发现范围

完整审计必须覆盖项目规则列出的全部相关仓库，以及仓库内以下来源：

- 路由、控制器、验证器、服务、模型、配置、协议和数据结构；
- 管理平台 API 封装、类型、页面、权限、菜单和构建；
- 客户端配置消费、连接、隧道、状态、资源、平台构建和发布流程；
- 节点核心配置解析、运行时、CLI、部署脚本和上报/命令通道；
- `test_*`、`*_test`、`verify_*`、`check_*`、`audit_*`、`*_regression` 等原生验证入口；
- 项目 `tools/`、`scripts/`、迁移入口、文档检查器和生成器；
- 回归目录自身、项目规范、接口文档、数据库说明和发布文档。

用户明确要求扫描 Codex 会话时，先确定授权目录和会话范围，再全量读取该范围，逐会话提取稳定契约、历史缺陷、曾用验证命令、环境阻塞和遗留已知失败。需要识别 Codex 误改后人工要求还原的重复返工时，必须按 [codex-rework.md](codex-rework.md) 的完整循环、误报排除、聚合和隐私边界处理。不得抽样，也不得把凭证、会话原文或短期运行值写入回归资产。

## 每项发现的归类

每个验证入口必须恰好归入以下一类：

- 普通自动化：进入 quick、standard、integration 或 build；
- 运行环境：进入 runtime，并在缺少依赖时返回 `BLOCKED`；
- 数据或结构迁移：进入 migration，只记录授权、备份、执行、回读、幂等和回滚证据；
- 真机验收：进入 real-device；
- 生产回读：进入 post-release；
- 明确禁止：保存禁止恢复的断言或分类证据，不执行被禁止入口；
- 已废弃：删除实现和所有引用，并用防回流检查守住边界。

不能稳定重复、无法判定副作用或依赖秘密值的脚本不得直接纳入 completion。先补隔离、脱敏、幂等和清理保证，或降级为证据门禁。

## 防遗漏门禁

审计至少验证：

1. 模块、检查、配置档和清单 ID 唯一且引用存在；
2. 模块依赖无环，触发仓库和路径有效；
3. 每项检查至少被一个模块引用，不存在空模块；
4. 每个原生清单条目指向已登记检查，新增验证文件不会漏登记；
5. 单体检查器的稳定检查 ID 恰好映射到一个业务板块；
6. `tools/` 和项目规定的脚本目录递归分类完整；
7. 已知失败具备精确指纹、原因、负责人和有效期，且过期即失败；
8. 报告目录、构建产物和临时证据不会误提交；
9. 数据库、Redis、队列和临时文件在成功与失败路径都能恢复且零残留；
10. 修改回归框架后先跑框架自测，再跑专项、changed 和 full/release 所需门禁。
11. 存在 Codex 重复返工清单时，晋升阈值、循环次数、截断哈希、检查引用、常驻板块映射和禁止原文字段全部有效。

技能自带 `audit` 负责结构与引用完整性；项目自己的框架自测必须继续负责文件发现、路径匹配、检查拆分和运行时行为。
